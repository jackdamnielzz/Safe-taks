## Current Problem & Root Cause

### The Issue
The running Next.js dev server loads its own instances of all modules. When we:
1. Seed data via POST /api/dev/seed-lmra or /api/dev/seed-stopwork
2. The data is written to the server's runtime `inMemoryStore`
3. But when we check the store from the controller process (Node.js scripts), it's empty
4. GET /api/stop-work returns empty because it queries the server's store, which may not persist between requests or may be using a different instance

### Why This Happens
- Next.js dev server uses hot module reloading and separate module resolution
- Each API route may get a fresh instance of server-helpers.js
- The `inMemoryStore` is not truly shared across all route invocations
- Module singletons don't work as expected in Next.js dev mode

### Implications
- We successfully created dev seed routes that return 200
- But the seeded data doesn't persist or isn't accessible to other routes
- This makes end-to-end testing via the running server challenging

## Technical Details

### Stop-Work Alert Schema
```typescript
{
  id: string;                    // e.g., "stopwork_1761904162573_6ryl5smp4"
  lmraId: string;                // Associated LMRA
  organizationId: string;        // Organization ID
  projectId?: string;            // Optional project ID
  triggeredBy: string;           // User ID who triggered
  triggeredByName: string;       // User display name
  triggeredAt: Date;             // Timestamp
  reason: string;                // Brief reason (max 100 chars)
  severity: 'moderate' | 'high' | 'critical';
  category: 'weather' | 'equipment' | 'personnel' | 'hazard' | 'other';
  description: string;           // Detailed description (max 500 chars)
  photoIds: string[];            // Optional photo references
  signature: {
    signerId: string;
    signerName: string;
    signatureData: string;       // Base64 signature image
    signedAt: Date;
  };
  status: 'active' | 'acknowledged' | 'resolved';
  acknowledgedBy?: string;
  acknowledgedByName?: string;
  acknowledgedAt?: Date;
  resolvedBy?: string;
  resolvedByName?: string;
  resolvedAt?: Date;
  resolutionNotes?: string;
  createdAt: Date;
  updatedAt: Date;
}
```

### Firestore Data Structure
```
organizations/{orgId}/
  ├── lmras/{lmraId}
  │   ├── id: string
  │   ├── title: string
  │   ├── description: string
  │   ├── status: 'active' | 'stop_work' | 'completed'
  │   ├── stopWorkAlertId?: string
  │   └── ...
  └── stopWorkAlerts/{alertId}
      └── (alert schema as above)
```
