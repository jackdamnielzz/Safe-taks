## 📋 Overview

Complete the LMRA workflow with robust offline support and emergency stop-work capability. This task ensures field workers can complete LMRAs without internet connectivity and have the authority to stop work immediately if conditions become unsafe.

## 🎯 Objectives

1. **Offline Sync**: Queue LMRA updates when offline, sync automatically when online
2. **Stop-Work Authority**: Allow field workers to trigger emergency work stoppage
3. **Conflict Resolution**: Handle concurrent edits and sync conflicts
4. **Real-Time Notifications**: Alert supervisors immediately when stop-work is triggered
5. **Audit Trail**: Log all offline actions and stop-work decisions

#### Retry Logic
```typescript
// Exponential backoff: 5s, 15s, 45s
const RETRY_DELAYS = [5000, 15000, 45000];
const MAX_ATTEMPTS = 3;

async function retryWithBackoff(fn: () => Promise<void>, entry: QueueEntry) {
  for (let attempt = 0; attempt < MAX_ATTEMPTS; attempt++) {
    try {
      await fn();
      return { success: true };
    } catch (error) {
      entry.attempts++;
      entry.lastAttempt = Date.now();
      entry.error = error.message;
      
      if (attempt < MAX_ATTEMPTS - 1) {
        await sleep(RETRY_DELAYS[attempt]);
      }
    }
  }
  
  return { success: false, error: entry.error };
}
```

#### Conflict Resolution
```typescript
// Strategy: Last-Write-Wins with timestamp
async function resolveConflict(local: LMRA, remote: LMRA): Promise<LMRA> {
  const localTime = local.updatedAt?.toMillis() || 0;
  const remoteTime = remote.updatedAt?.toMillis() || 0;
  
  if (localTime > remoteTime) {
    // Local is newer, use local
    return local;
  } else {
    // Remote is newer, use remote
    // Log conflict for audit
    await logConflict(local.id, 'remote_wins', { localTime, remoteTime });
    return remote;
  }
}
```

## 📝 Notes

### Existing Patterns to Follow
- **locationService.ts**: Excellent example of offline caching with localStorage
- **weatherService.ts**: Good example of retry logic and error handling
- **photoStorage.ts**: Reference for IndexedDB usage patterns

### Key Architectural Decisions
1. **IndexedDB over localStorage**: Larger storage capacity (50MB+ vs 5-10MB)
2. **Last-Write-Wins**: Simplest conflict resolution, acceptable for LMRA use case
3. **Optimistic UI**: Show success immediately, sync in background
4. **Event-Driven Sync**: Listen to online/offline events, auto-sync on reconnection
5. **Priority Queue**: Critical items (stop-work) synced first

### Security Considerations
- Stop-work alerts are high-priority, must sync ASAP
- Signature required for stop-work (prevent abuse)
- Audit trail for all offline actions
- Validate all queued data before sync (prevent tampering)

### Performance Considerations
- Batch sync operations (50 items per batch)
- Rate limiting (100ms delay between batches)
- Efficient IndexedDB queries (indexed by lmraId)
- Clean up old queue entries (>7 days)
